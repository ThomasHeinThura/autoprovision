# Spec A+B — Foundation

**Date:** 2026-08-08
**Status:** Awaiting approval
**Covers:** AI-DLC installation · repository structure · documentation alignment · host bootstrap · the nine review findings

Prerequisite for specs [C+D](2026-08-08-console-design.md) and [E+F](2026-08-08-database-secrets-design.md).
Nothing here changes what gets deployed to a customer VM.

---

## 1 · Goals

1. Install AI-DLC so it survives an upstream version bump without losing project context.
2. Give the repository a structure that holds as it grows from 31 workloads to ~45.
3. Remove the contradictions between the docs and the code, so the README can be trusted.
4. Fix the nine defects found in review, including two that can destroy production data.
5. Replace the manual 19-VM user creation with a verifiable workload.

**Non-goals:** the UI rewrite (spec C+D), new database engines (spec E+F), and refactoring
`main.py` beyond what the defect fixes require.

## 2 · AI-DLC installation

### The conflict

AI-DLC's install is `core-workflow.md` → `CLAUDE.md`. That file *is* the entire memory file, so
a straight copy erases any project-specific context, and hand-editing it means the next version
bump either clobbers your edits or forces a manual merge.

### Design

`CLAUDE.md` becomes **generated, never hand-edited** — the upstream workflow verbatim, plus a
delimited block appended from a file we own:

```text
CLAUDE.md                    generated — do not edit
├── (verbatim) aidlc-rules/aws-aidlc-rules/core-workflow.md
└── <!-- BEGIN PROJECT CONTEXT --> … <!-- END PROJECT CONTEXT -->
        ← generated from docs/project-context.md

.aidlc-rule-details/         verbatim copy of aws-aidlc-rule-details/
docs/project-context.md      hand-written, the only file you edit
scripts/install-aidlc.sh     regenerates CLAUDE.md deterministically
```

`scripts/install-aidlc.sh`:

| Step | Action |
| ---- | ------ |
| 1 | Locate the upstream — `--source` argument, else `../aidlc-workflows/aidlc-rules`, else fail with instructions |
| 2 | Read `VERSION`; record it in the generated header |
| 3 | Copy `core-workflow.md` → `CLAUDE.md`; sync `aws-aidlc-rule-details/` → `.aidlc-rule-details/` |
| 4 | Append the project-context block from `docs/project-context.md` |
| 5 | Print the installed rules version and a diff summary |

Idempotent, and safe to re-run after `git pull` in `../aidlc-workflows`.

`docs/project-context.md` holds what AI-DLC cannot know: that this is an on-premise IaC control
plane, that Ansible playbooks are the product, that `dist/` is committed deliberately, that the
jump host has no Node, and the pointer to `techstack.md`.

### `.gitignore` correction

The current file ignores `.claude` outright, which would silently exclude AI-DLC assets. Replace
with:

```gitignore
.claude/settings.local.json     # local overrides only
!.claude/settings.json
# .aidlc-rule-details/ and CLAUDE.md are committed — they are the installed ruleset
```

### Upstream

`../aidlc-workflows` stays checked out as the install source. It is a separate git repository and
is **not** vendored into `autoprovision/`.

## 3 · Repository structure

### Problem

Nine loose files at the root, including a 982 KB PDF and a 355 KB Excalidraw file. Documentation
is split across four top-level directories with no stated rule for which goes where, and the
README's repository map omits seven of the root entries.

```text
autoprovision/
├── CLAUDE.md                  generated by scripts/install-aidlc.sh

├── bootstrap-jumphost.sh
├── ansible.cfg
├── requirements.txt
├── .aidlc-rule-details/
│
├── app/                       control plane — what runs on the jump host
│   ├── main.py
│   ├── workloads.py           single source of truth for every workload (§5.1)
│   ├── content/               markdown for the Requirements / Guide / Theory tabs
│   └── dist/                  committed React build (spec C+D)
│
├── ui/                        React source — built off-host, never shipped
│
├── ansible/
│   ├── ansible.cfg → ../ansible.cfg   (symlink, or move; see §5.5)
│   └── *.yml
│
├── docker/
├── WSO2_APIM_KUBE_ISTIO/      team's repo — untouched, authoritative for WSO2
│
├── docs/
│   ├── project-context.md
│   ├── specs/                 these design documents
│   ├── planning/              ← moved from planning/
│   ├── runbooks/
│   │   ├── rke2/              ← moved from rke2-cluster/
│   │   └── mssql/             ← moved from mssql/
│   └── status/
│       └── service-status.md  ← moved from root
│
├── examples/                  ← echo.yaml, echo-argocd-app.yaml
├── assets/                    ← architecture.excalidraw, reference PDFs
└── scripts/
    ├── install-aidlc.sh
    └── stop-ui.sh             ← replaces kill.sh
```

### Rules that decide placement

| Directory | Holds |
| --------- | ----- |
| `docs/planning/` | What we decided to build and why — requirements, version matrices, sizing |
| `docs/runbooks/` | How to do it by hand when the automation is unavailable or you are debugging it |
| `docs/specs/` | How the tool itself is designed — these documents |
| `docs/status/` | What has actually been tested |
| `app/content/` | Text the console renders in the UI |
| `examples/` | Manifests demonstrating the platform, not part of it |

Every move breaks inbound links. **Every relative link in every markdown file is rewritten as
part of the move** and verified by a link checker added to pre-commit — the move is not complete
until that passes.

> **Open item.** `zz.sample_formats_v2_charco.pdf` (982 KB) is unidentified. It moves to
> `assets/` and is flagged for you to confirm or delete; nothing here deletes it.

## 4 · Host bootstrap

### Problem

README Step 0 requires SSHing into all 19 VMs by hand to create `autoprovision`. Un-audited,
un-repeatable, and the first place a mistake hides. It also forces password authentication
through the rest of the system, which is the root cause of two other findings.

### Design — two new workloads, both preceding everything else

#### `preflight` — reads only, changes nothing

Runs against any host list using **existing** credentials. Reports a pass/fail table:

| Check | Fails when |
| ----- | ---------- |
| SSH reachable on 22 | Host unreachable, or credentials rejected |
| OS release | Not an expected Ubuntu release for the intended role |
| Sudo available | The account cannot escalate |
| Free disk on `/` and the data mount | Under a per-role threshold |
| Time synchronisation | Offset over 1 s — breaks MSSQL AG certificate exchange and Kerberos |
| DNS resolution | The host cannot resolve its own name, or `127.0.1.1` is mapped (breaks Corosync) |
| Existing `autoprovision` account | Reports present or absent — not a failure either way |

Run this first, fix what it reports, then provision. It is cheap and catches the failures that
otherwise surface 40 minutes into an install.

#### `bootstrap-hosts` — creates the automation account

Runs as the **existing** admin account, not as `autoprovision`:

| Step | Action |
| ---- | ------ |
| 1 | Ensure an ed25519 keypair exists at `data/ssh/autoprovision` on the jump host (generate if absent, `0600`) |
| 2 | Create the `autoprovision` user on every target |
| 3 | Install the public key into `~autoprovision/.ssh/authorized_keys` |
| 4 | Write `/etc/sudoers.d/autoprovision` and validate it with `visudo -c` |
| 5 | **Reconnect as `autoprovision` using the key** and assert `sudo -n true` succeeds |

Step 5 is the point of the workload. Without it you have a script; with it you have a guarantee.

### Consequences

- Every later workload authenticates with the key. The SSH password field becomes optional and
  is used only by `bootstrap-hosts`.
- `_write_job_inventory` stops emitting `ansible_password=` and emits
  `ansible_ssh_private_key_file=` instead — closing finding #7 in the README's own security notes.
- The console's connection control shows **key** or **password** so the operator knows which is
  in use.

### Open questions for you

1. How are the VMs created — vSphere or Proxmox template, cloud-init, or manual ISO? If a
   template exists, the user and public key belong in it and `bootstrap-hosts` becomes a
   verification-only step.
2. Is the existing admin username the same on all 19 VMs? If not, the workload needs per-host
   credential overrides.
3. Confirm SSH keys are acceptable as the standing mechanism.

## 5 · Defect fixes

### 5.1 · Workload registry drift *(review finding #1 — structural fix)*

`ALL_TRACKS` in `main.py` is missing `sonarqube_up` and `sonarqube_clean`, which exist in the UI.
Their form values are silently discarded, and reset and log endpoints return 400. The runs
themselves succeed, so the failure is invisible.

Adding two strings fixes today's symptom and guarantees tomorrow's recurrence. **Fix the class
instead:** `app/workloads.py` becomes the single source of truth, defining for each workload its
id, group, ordinal, title, description, action, fields, step labels, dependencies, and
destructive flag. Then:

- `ALL_TRACKS` is derived — `[w.id for w in WORKLOADS]` — and cannot drift.
- A new `GET /workloads` endpoint serves the registry.
- The UI renders from that response and holds **no hardcoded workload list**.

This is a prerequisite for spec C+D, so it lands here.

### 5.2 · Run All can destroy production data *(finding #2 — highest severity)*

`PRIMARY` in the UI treats `mssql_ips` and `docker_ip` as "configured", and both are fields on
`mssql_clean` (tears down Pacemaker and the availability group) and `sonarqube_clean`
(`purge_data=true` wipes volumes and the database). Filling those cards once and clicking
**Run All Configured** executes them with no confirmation.

Fix:

- `workloads.py` marks each entry `destructive: bool`.
- Destructive workloads are **excluded from bulk run** in the backend, not only hidden in the UI —
  a bulk-run request naming one is rejected.
- They move to a separate Danger zone and require a typed confirmation token matching the target
  (AG name, or host address).
- `POST /tracks/start` requires `confirm: "<token>"` for any destructive workload and returns 400
  without it, so the guarantee survives a direct API call.

### 5.3 · Dead configuration key *(finding #3)*

`mssql_ip` appears in `PRIMARY` and `mssql-single-up` exists in `_track_plan`, but no card uses
either. Spec E+F reintroduces single-node provisioning properly; until then the key is removed
and the action is retained and marked internal.

### 5.4 · UAT database contradiction *(finding #4 — needs your decision)*

The README states UAT is one MSSQL single instance ([README.md:41](../../README.md), :137). The
UAT card runs `mssql-ag-up`, a three-node Pacemaker availability group. One is wrong.

**Recommendation: UAT is single-node.** UAT does not need to survive a 3am node failure; it needs
to exist, match production's schema, and be quick to rebuild. Three VMs and a consensus layer for
a test environment is production's budget spent in the wrong place. Spec E+F makes this a
per-deployment choice regardless, so this decision sets the default rather than a constraint.

**Blocked on your answer.** VM count, sizing docs, and the WSO2 JDBC target all follow from it.

### 5.5 · Wrong `ansible.cfg` path in the README *(finding #5)*

The README says `ansible/ansible.cfg`; the file is at the repository root. Ansible resolves
`ansible.cfg` from the working directory, and `main.py` runs playbooks with `cwd=BASE_DIR`, so
the root location is correct and the **documentation** is what changes.

### 5.6 · Stale card table in the README *(finding #6)*

Step 3's table describes cards named "GitLab (shared)", "Prod RKE2 Cluster", "UAT MSSQL". The UI
ships numbered per-environment steps. Once `workloads.py` exists the table is **generated** from
it by `scripts/gen-readme-tables.py`, run in pre-commit, so it cannot go stale again.

### 5.7 · Root clutter *(finding #7)* — handled by §3.

### 5.8 · `.gitignore` ignores `.claude` *(finding #8)* — handled by §2.

### 5.9 · `CLUSTER_TYPE` contradiction *(finding #9 — new)*

[README.md:236](../../README.md) describes the production AG as `CLUSTER_TYPE=NONE` (read-scale,
no automatic failover, no listener). The UI card descriptions and
[service-status.md](../status/service-status.md) both say `CLUSTER_TYPE=EXTERNAL` (Pacemaker,
synchronous, automatic failover). These are materially different products — one fails over
automatically and one does not.

The lab record is the authority: **`EXTERNAL` with Pacemaker is what was built and tested.** The
README is corrected, and the distinction is written up in spec E+F, where it becomes the
difference between the "bilateral" and "cluster" HA shapes.

how it is actually done.** Each cross-links the other two.

## 8 · Risks

| Risk | Mitigation |
| ---- | ---------- |
| The folder move breaks links no one notices for months | Link checker in pre-commit, added in the same change |
| `workloads.py` is a large refactor of `_track_plan` | The registry describes workloads; `_track_plan` keeps building execution plans. Data and behaviour stay separate. |
| Generated `CLAUDE.md` is edited by hand and the edit is lost | A generated header says so, and `install-aidlc.sh` refuses to overwrite if the delimiters are missing |
| Key-based SSH locks out a host mid-rollout | `bootstrap-hosts` verifies before the password path is retired; the password field stays available as a fallback |
